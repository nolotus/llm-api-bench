# 测量与结果标准 (RESULTS STANDARD v1)

本文件定义"什么算一个可比较的数据点"以及"怎样报告"。任何不满足本标准的数字，不得进入结论。

---

## 1. 维度（每个数据点必须标注全部维度）

| 维度 | 取值 | 说明 |
|---|---|---|
| provider / tier | 五家 × 各自档位 | 档位必须实测存在，不能凭推测 |
| context_tokens | 1K / 4K / 16K / 32K | **按真实 prompt_tokens 记录**，目标是换算依据，不是事实 |
| cache_state | cold / warm / growth-N / ttl-{gap}s | cold = 该前缀首次出现（同一 (provider,tier,run) 内唯一） |
| concurrency | 1 / 2 / 4 / 8 / 16 / 32 | 同批在途请求数 |
| output_cap | 512（默认）/ 1024（思考链长的供应商） | 低于实际思考长度会被截断，样本作废 |

## 2. 每请求必采字段

- `started_at_utc`、`http_status`、`done`
- `first_token_ms`：首个生成 token（可能是思考链）
- `first_content_ms`：首个正文 token；**为 null 表示本次未产出正文，不得记为 0**
- `total_ms`
- `usage`: `input_tokens` / `output_tokens` / `cached_input_tokens`（缺失记 unknown，不得填 0）
- `chunk_times_ms`：流式到达时间序列（限长），用于算卡顿
- `finish_reason`
- `cost_estimate`：按配置单价 × usage 计算，标注"估算非账单"

## 3. 派生指标

- **缓存率** = `cached_input_tokens / input_tokens`。`cached` 缺失或 `cached > input` 时判为**无效**，不参与统计。
- **缓存合理性校验**：若 `cached == input - 1`（或其它恒定偏移）连续出现，视为**上报假象**，单列并在结论中标注不可信。
- **TPS** = `output_tokens / (last_chunk_ms - first_content_ms)`，仅在正文存在时计算。
- **卡顿** = 相邻 chunk 间隔的最大值与 P95；需排除首包前等待。
- **降级比** = `P50(C=n) / P50(C=1)`，同 provider/tier/context/cache_state 下比较。

## 4. 统计口径

- 每格（provider × tier × context × cache_state × concurrency）**n ≥ 5** 才出分位数；n < 5 只报原始值。
- 报：`n / min / P50 / P90 / P99 / max / mean`。
- 异常值：用 `1.5 × IQR` 标记，**保留不剔除**，单独列出 max 与离群原因。
- 缺失值：`null` 与 `unknown` 分开统计，**任何情况下不得用 0 代替**。
- 比较两个配置时，必须同 context、同 cache_state、同 concurrency、同 output_cap。

## 5. 并发阶梯

- 档位：**1 / 2 / 4 / 8 / 16 / 32**（不止 5）。
- 每档至少 2 轮，避免单次抖动被当成降级。
- 停止条件：出现 429 连续 3 次、错误率 > 20%、或预算触顶。**停止不代表该档不可用，只是本次未测完**。
- 并发测的是"客户端发起在途数"，不是服务端真实并发，报告中必须写明这一限制。

## 6. 缓存曲线

1. **增长曲线**：1K→2K→4K→8K→16K 追加式上下文（后轮严格包含前轮全文），记录每轮 cache 率与 first_token。
2. **稳态命中**：同前缀冷启动后连发 n≥5 次暖请求，报分布。
3. **存活曲线**：冷启动后停顿 15s / 60s / 180s 再发，记录是否仍命中。
4. **理论上限对照**：增长场景中 cache 率上限 = `上一轮 tokens / 本轮 tokens`，实测值与理论上限并列展示。

## 7. 完整性、断流与截断（必须统计，不能只看成功请求）

一次请求"返回 200"不等于"输出完整"。必须区分下列情形，并分别计数：

| 情形 | 判定依据 | 归类 |
|---|---|---|
| 正常结束 | `finish_reason = stop` 且收到流末尾 `[DONE]` | `complete` |
| 达上限截断 | `finish_reason = length` | `truncated`（**不算失败，但正文可能被思考链吃掉**） |
| 流中断 | 连接关闭但未收到 `[DONE]` | `stream_break`（**失败**） |
| 正文缺失 | `finish_reason = length` 且 `first_content_ms = null` | `no_content`（**无可用输出**） |
| HTTP 异常 | 4xx / 5xx | `http_error` |
| 超时 | 客户端超时未收完 | `timeout` |
| 限流 | 429 | `rate_limited`（触发停止规则） |

### 停顿（stall）—— 重点指标

"整体速度很快，但输出到某个 token 时突然停几秒"是独立于带宽和总耗时的体验杀手，必须单独量化：

- **定义**：相邻两个 **正文 chunk** 的接收时间间隔（客户端 `monotonic` 计时）。
- **`stall_max_ms`**：单次请求内的最大间隔。
- **`stall_count_1s` / `stall_count_3s`**：该请求中间隔 ≥1s / ≥3s 的次数。
- **`stall_rate`**：出现 ≥1s 停顿的请求数 / 有正文的请求数。
- 同时报 `stall_max_ms` 的分布：`P50 / P90 / P99 / max`（跨请求）。

报告时必须把 stall 与总耗时并列，因为两者会背离：
一个请求总耗时可能只有 3 秒，但其中 2.5 秒是中途停顿。

### 必报指标

- **有效正文产出率** = `complete + truncated(有正文)` / 全部请求
- **彻底无正文率** = `no_content` / 全部请求
- **断流率** = `stream_break` / 全部请求
- **首包后卡死率** = 收到首 token 但 90s 内未结束 / 全部请求
- **卡顿** = 相邻 chunk 间隔的 `max` 与 `P95`（排除首包前等待）
- **重试次数**：本基准**不自动重试**；一旦发生重试必须单列，并用新的 request_id

### 报告要求

完整性指标必须与延迟/缓存指标**并列出现在同一张表**，不得只报成功的那些请求。
若某供应商 `no_content` 比例高（例如输出预算 512 时思考链吃满），必须在表下注明"该配置下正文不可用，延迟数据仅代表首 token"。

## 9. 长期运行指标（持续压测）

单次批次的 P50 不能代表长期表现。持续运行必须报下列各项：

### 9.1 尾部而不是中位数

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| `P95 / P99 / max` | 分位数 | 用户投诉来自尾部，不是中位 |
| `bad_rate(>3s)` / `bad_rate(>5s)` | 超过阈值的请求占比 | SLO 口径，可直接写进产品要求 |
| `worst_bucket` | 分时间桶里最差一段的 P95 | 抓“某一小时突然变慢” |

### 9.2 漂移（drift）

把持续压测按 5 或 10 分钟分桶，报每桶 `P50 / P95 / n / 错误数`，并给出斜率判断：
- 若 P95 逐桶上升 → 存在累积退化（限流、连接池、内存）
- 若首桶明显高于后续桶 → 那是缓存预热成本，不是退化

### 9.3 稳定性

- `error_rate`（非 200 / 断流 / 超时）
- `retry_count`（本基准不自动重试，出现即单列）
- `no_content_rate`（有 200 但无正文）
- `stall_rate`（出现 ≥1s 中途停顿的请求占比）

### 9.4 缓存与长期的交叉

- **预热曲线**：第 1 次、第 2 次、第 3 次…命中率如何上升
- **稳态命中率**：连续同前缀请求的命中中位数
- **亲和前提**：必须带 `x-session-affinity`，否则副本路由会让命中率归零（本基准曾因此得出错误结论）

### 9.5 样本量要求

| 目的 | 每格最小 n |
|---|---|
| 报 P50 | 20 |
| 报 P95 | 60 |
| 报 P99 | 200 |
| 判断漂移 | ≥5 个时间桶 |

不足时只报原始值，并注明"P99 等同 max，不具统计意义"。

## 10. 禁止的表述

- 不写"全网最快/最便宜/第一/智商税/负优化"。
- 不把估算费用写成账单。
- 不把单次采样当结论；不把并发客户端数当服务端容量。
- 不使用不同 context / 不同 cache_state 的数据相互比较。
- 对未解释的差异（如 Baseten 缓存与文档不符），标注"未解释"，不代其编原因。

## 8. 数据落盘

- 原始：`results/<stage>/<provider>-<tier>-<mode>.jsonl`（含每请求字段）
- 汇总：`results/<stage>/RESULTS.md`（按本文件格式）
- 账本：每次请求 reserve/settle 记录，未知用量保留上界
