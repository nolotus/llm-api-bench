# Matrix-v1 评测报告勘误与方法论复盘清单 (CORRECTIONS)

> **文档性质**：本文档为 2026-10-20 执行的 Matrix-v1 基准评测的技术勘误与复盘清单。
> 
> **责任声明**：旧版报告中出现的数据错位、口径混淆与过度定性，**核心责任完全在于我方测试脚本实现缺陷、口径定义混乱及分析外推不当**，并非供应商服务质量问题。
> 
> **公开边界说明**：Matrix-v1 实测数据**不能作为供应商排名或选购建议的结论**；但勘误清单、方法局限及原始数据记录（raw records）保持完整存证并可公开查验，供技术复盘与社区监督。本次处理为**报告口径更正，绝非删除或掩盖原始数据**。

---

## 一、 核心错误逐条纠正与物理事实核验

### 1. 核心测试条件失配：Prompt Token 组装偏差（我方脚本错误）
- **旧版报告说法**：将 LithosAI 与四家公有云服务（DeepSeek 官方、Baseten、DeepInfra、Fireworks）在 1K~32K 各档位直接并列对比并排序。
- **物理事实核查**：
  - 测试脚本预设的目标尺寸为十进制标称值：`SIZES = [1000, 4000, 16000, 32000]`（decimal tokens，非二进制 1024/4096/16384/32768）。
  - 四家公有云由于脚本上下文填充逻辑错误，实际发送的输入 tokens 仅为：1K 档约 360~400、4K 档约 1280~1330、16K 档约 4950~5020、32K 档约 9870~9940。
  - LithosAI 历史测试填充接近标称目标：1K 档约 1030~1060、4K 档约 3990~4060、16K 档约 15930~16040、32K 档约 31900~32000。
  - LithosAI 采用的是历史基准协议，并非 matrix-v1 协议，亦非同批同矩阵执行。
- **纠错判定**：公有云实际输入的 Prefill 计算量仅为 LithosAI 的约 31%~35%。输入长度相差近 3 倍，直接并列对比属于我方实验控制变量失败，横向性能排名完全不成立。

### 2. 窄时间窗口与跨时段缺乏对照
- **旧版报告说法**：将数分钟内的瞬态测试结果外推为各平台综合与全天稳定性表现。
- **物理事实核查**：
  - 所有记录的 UTC 时间窗口均为**首末请求发起时间（`started_at_utc`）的范围，并非请求完成耗时**。
  - LithosAI 首末请求发起范围为 UTC 02:48:15 .. 04:49:02，跨度约 2 小时 01 分（由 formal 931 条 + pilot 23 条构成，共 954 条，并非全部正式样本；pilot 为初期有效验证样本，非探针或重试）。
  - 四家公有云首末请求发起范围集中在 UTC 05:52 .. 06:04，各档跨度仅 3 至 12 分钟（每档 63 次）。
- **纠错判定**：公有云 API 响应可能受测试时段影响，但**本次测试在公有云上仅有极短时间窗口，没有受控的跨时段对比证据**。将短跑快照直接包装为供应商长效性能结论，属于缺乏对照组的过度推断。

### 3. 指标统计定义混淆与数值失实
- **旧版报告说法**：在“首包延迟（TTFT）”列中给出官方 670.8 ms、Baseten 670.0 ms、Baseten Fast 822.8 ms 等数值并标注为中位数。
- **物理事实核查**：
  - 上述数值系旧脚本计算的算术平均值（Mean），而非中位数（Median）。
  - 以 DeepSeek 官方为例，其实测均值实际约为 708.0 ms，旧报告声称的 670.8 ms 在数学上不成立。
  - 旧报告中的 TPS、费用及缓存数据混杂了未对齐输入长度与不同 reasoning 状态的样本。
- **纠错判定**：全数撤回旧汇总性能榜单。待后续按 `kind`、`actual input tokens`、`tier`、`reasoning status` 及 `成功状态` 细分分层重算。

### 4. 字段物理记录误读与无正文归因偏差
- **旧版报告说法**：“短文本吃不到正文，`first_content_ms` 为 0”，“平台强制注入激进的思维链”。
- **物理事实核查**：
  - 原始 records 记录中，正文到达时间字段物理值为 **`null`**，而非数值 `0`。我方将 `null` 记为 `0` 属于低级数据记录错误。
  - 在 `max_tokens=32` 的短预算下，模型返回了 reasoning 内容并因长度超限截断（`finish_reason="length"`）。
  - 并非所有 Baseten 记录都能仅凭字段证明全部 32 个 token 都是 reasoning。且该正文为 null 和 length 截断现象在 DeepSeek 官方与 Fireworks 同样出现。
- **纠错判定**：这是大模型在受限输出预算下的行为表现，不能声称供应商“强制注入”或“激进”，亦不能声称全部 32 token 均被 reasoning 占满。

### 5. 校验失败归因与成本未知状态核实
- **旧版报告说法**：“0 失败 / 0 掉线”，“账本已全额结清”。
- **物理事实核查**：
  - Baseten Fast 记录中存在 2 条异常：`invalid_usage` 与 `model_mismatch`。两次请求服务端均返回了 HTTP 200，中断由我方客户端适配解析与模型字段校验触发，并非服务商网络断流或平台宕机。
  - **两条 HTTP 200 请求服务端仍可能已产生计费，但金额未知**。
  - 预算账本将未产出实际金额的请求置为 `settled_unknown`。保留上限额度（每笔 $0.00128745，两笔合计 **$0.0025749**）仅为预算系统的内部保留占用（Hold），**并不代表实扣，也不代表零消费**。
  - **压测探针脚本未挂载 ledger 直连发包，因此全部 API 成本未知**，无法声称账本覆盖全量 API 成本。
- **纠错判定**：旧报告宣称“0 失败”和“全额结清”与物理事实不符，现予核准纠正。

### 6. 压测口径错位与概念混淆
- **旧版报告说法**：将 C=30 压测耗时直接与流式 TTFT 并列对比。
- **物理事实核查**：
  - `stress_probe.py` 采用 `stream=False, max_tokens=16`，测量的是客户端非流式完整 HTTP 请求往返耗时，**绝非流式首包时间（TTFT）**。
  - 旧报告将单批次突发中的单次最差延时与典型中位数并列，并偷换为流式 TTFT，属于严重的统计口径误导。
  - 压测为单批次突发（$n=30$），各家均返回 30/30 HTTP 200，既不能衡量持续在途并发承载力，亦无精确 UTC 与 usage 记录。为避免继续误导，删除原报告中具体的非受控延时数字对比。

### 7. 统计指标与分位数口径撤销
- **旧分位数汇总撤下，未核准或 null 不作为有效指标；未来报告经验分位需说明方法与样本量**。
- **生成流速**：旧报告 TPS 仅为 $N=3$ 的 512 token 接收 chunk 间隔近似值，非服务端底层解码纯流速。
- **缓存命中率**：严格按 exact tier 统计有效返回，未返回者标为 `unknown`，`rep > 0` 不代表命中。

### 8. 情绪化定性与营销断言全面撤回
- 撤回“全网第一”、“全网最暴烈”等夸大性词汇；
- 撤回“智商税”、“负优化”、“纯属浪费预算”等情绪化主观攻击措辞；
- 撤回“官方全网最便宜”等自相矛盾说法（同表按配置价计算 DeepInfra 估算值更低）；
- 撤回一切对供应商后端机制的主观猜测。

## 二、 当前测试尚未覆盖的关键维度（待补测项）

为防止未来基准再次出现结论片面性，以下维度明确列为**当前数据集未覆盖项**：

1. **缓存机制与存活周期 (TTL) 探测**：尚未系统测试不同前缀、不同间隔时间下的 KV Cache 复用与过期时间。
2. **持续并发下的流式速率退化 (Sustained Concurrency × Streaming TPS)**：尚未实测在持续在途并发压力下，各家流式 TTFT 与真实解码速度的衰退曲线。
3. **同等受控条件下的多时段比对**：尚未在严格相同输入长度与环境下进行跨时段对比。
4. **Fireworks fast 档位适用性核验**：当前仅测 Serverless 默认档位，未测 fast 路由。
5. **LithosAI 完整原始流式数据补齐**：历史数据缺乏同等细粒度的流式分块 raw 事件记录，无法支撑与其他平台在同等流式口径下的横向比对。

---

## 三、 复盘总结

- **基准状态**：Matrix-v1 性能榜单全面撤回；不作为供应商排名或选购结论。
- **证据存留**：所有原始日志与 records 保持原状存证供核验。
- **整改准则**：未来任何新基准必须首先修复测试脚本的输入长度对齐问题，严格分离流式与非流式口径，并在展示任何统计值时明确数学定义与样本边界。
