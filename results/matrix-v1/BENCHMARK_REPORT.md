# DeepSeek 模型多供应商 API 实测技术记录与数据复盘 (Matrix-v1)

> **状态声明**：**本报告不能作为供应商横向排名或选购建议的结论（NOT READY FOR RANKING / PURCHASING DECISIONS）。**
>
> 经 2026-10-20 全量数据核算与独立技术审计，旧版公开报告存在严重的方法论与口径错误。核心责任在于**本次测试脚本设计缺陷及报告统计口径失误**，而非供应商服务问题。主要错误包括：测试脚本中输入 Token 填充失配达 2.5~3 倍、将不同时间窗口的狭窄样本进行不可比对照、将字段 `null` 误写为 0、将本地理论估算混同于实际扣费账单，以及将单批短突发请求耗时偷换为流式 TTFT。
>
> 为保证技术真实性，**原报告中所有未经受控重算的性能数值榜单全数撤回**。本文档记录经物理日志核验的客观事实，保留底层原始数据（raw records）以供技术复盘。

## 2. 核心实验条件失配：Prompt Token 长度悬殊

经核对原始 records，本次测试脚本在填充上下文时存在严重实现偏差：四家公有云实际发送的 Prompt Token 远低于目标预设，而 LithosAI 填充接近预设。这属于**我方测试脚本在文本组装逻辑上的错误**：

| 实验目标档位 (Decimal) | 目标上下文预设 | 四家公有云实际 Prompt Tokens | LithosAI 历史正式基准实际 Prompt Tokens | 实际偏差情况 |
| :---: | :---: | :---: | :---: | :--- |
| **1K 档** | 1,000 tokens | 约 360 ~ 400 tokens | 约 1,030 ~ 1,060 tokens | 公有云实际输入仅为 Lithos 的 ~35% |
| **4K 档** | 4,000 tokens | 约 1,280 ~ 1,330 tokens | 约 3,990 ~ 4,060 tokens | 公有云实际输入仅为 Lithos 的 ~32% |
| **16K 档** | 16,000 tokens | 约 4,950 ~ 5,020 tokens | 约 15,930 ~ 16,040 tokens | 公有云实际输入仅为 Lithos 的 ~31% |
| **32K 档** | 32,000 tokens | 约 9,870 ~ 9,940 tokens | 约 31,900 ~ 32,000 tokens | 公有云实际输入仅为 Lithos 的 ~31% |

**结论**：在 Attention Prefill 阶段，算力消耗与上下文长度直接正相关。将输入仅为 9.9K tokens 的公有云测试结果，与输入达 32K tokens 的 LithosAI 测试结果并列对比，违背了单一变量控制原则，所产生的任何性能排序均不成立。

## 3. 性能数据撤回与分层重算说明

**旧汇总性能榜单全数撤回**。

撤回原因核实：
1. **指标统计定义混乱**：旧版报告标题标注为中位数（median），但表中填写的 670.8 ms、670.0 ms、822.8 ms 实际为脚本旧算术均值，而非中位数。以 DeepSeek 官方为例，其实测均值实际约为 708.0 ms，旧报告所称 670.8 ms 在数学上不成立。
2. **生成速率与成本混杂**：旧表中的 TPS、理论费用及缓存命中率，混杂了未对齐输入长度、未分层隔离 reasoning 以及样本量极小的片面数据。
3. **分位数指标未达有效性门槛**：在小样本或未经独立复核场景下，高分位数统计未核准或为 null 的数据不得作为有效指标呈现。

**后续处理方案**：旧汇总撤回，待按 `kind`、`actual input tokens`、`tier`、`reasoning status` 及 `成功状态` 分层重算。在分层清洗完成前，本报告不保留供应商 TPS、理论费用及缓存旧数字，以免继续误导。

## 4. 关键技术现象与实测归因

### 4.1 短输出预算截断与 `first_content_ms=null`
- **原始观察**：在 `max_tokens=32` 的短输出测试用例中，原始日志记录到模型产生了 reasoning 输出，随后因达到长度上限以 `finish_reason="length"` 结束，字段记录为 `first_content_ms=null`。
- **事实归因**：并非所有记录都能仅凭返回字段证明全部 32 个 token 均被 reasoning 占满；但可以确认在 32 token 的严格限制下，模型尚未输出正文即达到配额截断。
- **责任与纠偏**：
  - 该现象在 DeepSeek 官方和 Fireworks 的 `max_tokens=32` 用例中同样出现，是大模型在受限输出预算下的行为表现。
  - 我方旧报告将 `null` 误记为 `0`，并主观推断为服务商“强制注入激进思维链”，属于严重事实误读与不当推断，现予撤回纠正。

### 4.2 Baseten 客户端校验异常与账本 Unknown Hold
- **原始观察**：Baseten Fast 档 63 次请求中，有 2 条记录显示未正常完成：
  1. `status="invalid_usage"`, `computed_usd=null`
  2. `status="model_mismatch"`, `computed_usd=null`
- **事实归因**：两次请求服务端均返回了 HTTP 200，中断发生在客户端本地适配器对返回结构与模型名称的校验阶段。这属于我方客户端适配与校验逻辑问题，并非服务商网络断流或宕机。
- **账本与成本状态核实**：
  - 这两条 HTTP 200 请求服务端仍可能已产生实际计费，但金额未知；
  - 预算系统因未获取到确定的实际消费金额，将两笔请求置为 `settled_unknown` 状态。预扣上限额度（每笔 $0.00128745，合计 **$0.0025749**）仅为预算系统的保留占用（Hold），**并不代表实扣，也不代表零消费**。旧报告宣称“0 失败”和“账本已全额结清”与物理事实不符。

### 4.3 DeepInfra Standard 与 Priority 档位观察
- **原始观察**：在 UTC 05:52~06:00 期间的这批样本中，Priority 档（配置加价 50%）的汇总耗时略高于 Standard 档。
- **事实归因**：这仅代表在该特定短时间窗口及特定请求参数下的实测记录。我方本次并未进行受控的多时段测试，没有证据推断服务商后端的拥堵状态或调度策略。旧报告宣称其为“负优化”或“纯属浪费预算”属于不当推断。

### 4.4 压测（Stress Probe）的真实口径
- **原始观察与参数**：`stress_probe.py` 采用 `stream=False, max_tokens=16`，由客户端线程池发出一批并发请求（$n=30$）。
- **口径纠正**：
  - 该脚本测量的是非流式整请求接收耗时（从连接建立至 `resp.read()` 接收完毕），**绝非流式 TTFT**。
  - 旧报告将单批次非流式单次最差耗时与中位数值混同并与流式指标并列，属于严重的统计口径错位。
  - 单批短突发（$n=C$）即使各平台均为 30/30 HTTP 200，既不能代表持续在途并发承载能力，也无法测量流式流速，且该脚本无精确 UTC 时间与 usage 记录。为避免口径误导，此处不展示任何非受控的具体数值。

## 5. 成本与预算覆盖边界说明

1. **理论估算并非实付账单**：原报告中的费用数字系通过模型返回 Token 乘以本地配置文件中的单价估算得出（`computed_usd`），并非月结扣费或信用卡实际扣款账单。各单价未经全量核准。
2. **两条 HTTP 200 仍可能产生费用**：Baseten 校验失败的两条请求服务端返回了 HTTP 200，服务端仍可能已计费，实际金额未知；$0.0025749 仅为预算系统内部保留占用额度，既不代表实扣，也不代表零消费。
3. **探针无 ledger 因此全部 API 成本未知**：我方现有的 `BudgetLedger` 仅覆盖了 `matrix_bench.py` 请求，所有压测探针脚本（`stress_probe.py`、`concurrency_probe.py`、`mega_stress.py`）均未挂载 ledger 直连发包，因此探针部分消耗的实际 Token 与 API 成本完全未知，无法给出全部 API 成本覆盖的结论。

## 6. 后续基准改进要求

在解决以下问题前，不进行任何横向对比排榜：
1. **修正输入组装逻辑**：修复测试脚本，确保 1,000 / 4,000 / 16,000 / 32,000 decimal 上下文测试用例在所有供应商处的真实 Prompt Tokens 严格对齐。
2. **规范分层统计流程**：流式首字（TTFT）、首个正文（Content Arrival）、纯解码流速、非流式耗时必须严格分流处理，不混为一谈。
3. **明确分位数计算规范**：未来报告经验分位数需说明具体计算方法与样本量前提，未核准或样本不足的高分位指标不作为有效指标呈现。
